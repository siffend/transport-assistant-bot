# ИИ-ассистент для работы с обращениями пассажиров общественного транспорта

Прототип чат-бота первой линии поддержки для Telegram: по сообщению пассажира
определяет намерение, находит подтверждение в базе знаний, формирует ответ
**со ссылкой на нормативный или официальный источник**, а при нехватке данных
честно сообщает об этом и передаёт обращение оператору.

Регион: Тульская область. Источник данных — файл `data/source/khakaton.xlsx`
(21 тестовый вопрос с полями «Вопрос», «Короткий ответ», «НПА», «Ссылка»).

---

## 1. Что умеет прототип

| Требование задания | Как реализовано |
|---|---|
| Отвечать на типовые вопросы (тарифы, оплата, льготы, проездные, валидаторы, списания, уведомления) | База знаний из 27 атомарных документов, покрывающая все 21 исходный вопрос |
| Находить релевантный нормативный/справочный источник | Гибридный поиск: совпадение по формулировкам + символьные n-граммы + покрытие запроса |
| Показывать источник и ссылку | Каждый ответ сопровождается блоком «Источник: НПА» и ссылкой; покрытие источниками — 100 % |
| Обрабатывать переформулированные и разговорные вопросы | Стеммер Портера, словарь разговорных синонимов, несколько «поверхностей» на документ |
| Не выдумывать ответ при отсутствии данных | Пороги уверенности + лексикон предметной области + проверка заземления ответа LLM |
| Уточнять при нехватке существенного параметра | Слоты уточнений с кнопками (например, категория льготника) |
| Единый интерфейс чат-бота | Telegram-бот (long polling и webhook) + веб-демо на том же ядре |

Дополнительно: распознавание вопросов о **других регионах** (ответ «вне зоны
ответственности»), явная пометка ответов, под которыми **нет нормы**, и
эскалация на оператора по запросу пассажира.

## 2. Архитектура

```
        Telegram (long polling / webhook)        Веб-демо (Flask)
                     │                                 │
                     └──────────┬──────────────────────┘
                                ▼
                       assistant/pipeline.py
                       политика ответа: интент → поиск → решение
                                │
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
 assistant/text.py      assistant/retriever.py      assistant/llm.py
 нормализация,          гибридный поиск,            генерация поверх
 стемминг, синонимы     сигналы уверенности         контекста (опционально)
                                │
                                ▼
                      data/kb/*.json — база знаний
        base_from_xlsx.json (автогенерация) + curated.json (редактура)
        + clarify.json (уточнения) + domain_lexicon.json (зона темы)
```

### Почему не «просто LLM»

LLM в прототипе **опциональна и выключена по умолчанию**. Ответы берутся из
базы знаний дословно, поэтому тариф или телефон невозможно «придумать».
Если LLM включена (`LLM_ENABLED=1`), она только переформулирует найденный
контекст, и её ответ проходит **проверку заземления**: любое число, которого
нет в переданных фрагментах, отбраковывает генерацию и возвращает
экстрактивный ответ (`assistant/llm.py`).

### Как принимается решение

`assistant/pipeline.py`, по порядку:

1. команда/приветствие → карточка возможностей;
2. ответ на ранее заданное уточнение → ответ выбранным документом;
3. просьба позвать оператора → эскалация с контактами;
4. упоминание другого региона → «вне зоны ответственности»;
5. релевантность ниже нижнего порога **или** запрос не опознан как транспортный → «данных нет» + оператор;
6. выбор варианта внутри интента (город/пригород, школьник/взрослый);
7. не хватает существенного параметра → уточняющий вопрос с кнопками;
8. серая зона уверенности → предложение формулировок, а не угадывание;
9. иначе → ответ + НПА + ссылка.

### Сигналы релевантности (`assistant/retriever.py`)

Все сигналы ограничены диапазоном [0..1], чтобы по абсолютному значению можно
было принимать решение «отвечать / уточнить / отказаться»:

| Сигнал | Смысл | Вес |
|---|---|---|
| `surface` | лучшее совпадение с одной из формулировок документа (вопрос, заголовок, перефразировки, ключевые слова) | 0.45 |
| `body` | совпадение с телом ответа | 0.15 |
| `coverage` | доля веса запроса (по idf), покрытая документом | 0.25 |
| `domain` | сколько «ядерных» терминов документа узнано (нечёткое сравнение по 5 буквам) | 0.15 |
| `on_topic` | есть ли в запросе хотя бы один термин транспортного лексикона | фильтр |

Именно `on_topic` отличает «сколько стоит проезд» от «сколько стоит бензин»:
формулировки похожи, но во втором случае предметных терминов нет, и бот
отказывается отвечать вместо того, чтобы выдать тариф на автобус.

## 3. Результаты оценки

`python eval/run_eval.py` — 67 случаев: 21 исходный вопрос, 32 разговорные
переформулировки, уточнения, эскалации, 3 вопроса о других регионах и 7
вопросов не по теме.

| Метрика | Основной набор | Контрольный набор |
|---|---|---|
| Doc@1 — верный документ на первом месте | **100 %** (53/53) | 70 % (7/10) |
| Doc@3 | **100 %** | 90 % |
| Policy — верный тип реакции (ответ/уточнение/отказ) | **100 %** (67/67) | **100 %** (15/15) |
| Ответы с указанием источника | **100 %** | 100 % |
| Отказ на вопросах не по теме | **100 %** (7/7) | 100 % (4/4) |
| Латентность (медиана) | **1.2 мс** | 1.2 мс |

Контрольный набор (`eval/holdout.json`, 15 случаев) написан **после** настройки
порогов и словарей и в настройке не участвовал — он показывает качество без
подгонки. Порядок документов там слабее (70 % Doc@1), но ни один вопрос не
получил выдуманного ответа: тип реакции верен в 100 % случаев, а правильный
документ в 90 % случаев находится в топ-3.

Известные ограничения честно зафиксированы в `eval/holdout.json`: на вопросах
на стыке тем («какая сумма спишется, если приложить обычную дебетовую карту»)
бот выбирает соседний документ той же области.

Запуск:

```bash
python eval/run_eval.py --verbose          # основной набор, по каждому случаю
python eval/run_eval.py --testset holdout.json
python eval/run_eval.py --json report.json # машиночитаемый отчёт
python -m unittest discover -s tests -v    # 18 модульных тестов
```

## 4. Запуск

Требуется Python 3.10+. Ядро работает **без внешних зависимостей** (только
стандартная библиотека); Flask нужен для веб-демо, openpyxl — для пересборки
базы из Excel.

```bash
pip install -r requirements.txt
```

### Telegram-бот

1. Получить токен у [@BotFather](https://t.me/BotFather).
2. Запустить:

```bash
export TELEGRAM_TOKEN="123456:AA..."
python run_bot.py
```

Режим long polling подходит для демонстрации. Для продакшена — webhook:

```bash
export TELEGRAM_TOKEN="..." WEBHOOK_SECRET="случайная-строка"
python run_web.py                     # поднимает /telegram/webhook
python -c "from assistant.telegram_bot import TelegramAPI; \
           import os; TelegramAPI(os.environ['TELEGRAM_TOKEN']).set_webhook(
           'https://ваш-домен/telegram/webhook', os.environ['WEBHOOK_SECRET'])"
```

### Веб-демо (без токена)

```bash
python run_web.py     # http://127.0.0.1:8000
```

В демо видно то, что скрыто в мессенджере: тип реакции, интент, уверенность,
идентификатор документа и — по галочке — отладку поиска с разложением по
сигналам. Удобно показывать жюри.

### Подключение LLM (необязательно)

```bash
export LLM_ENABLED=1
export LLM_BASE_URL="https://api.openai.com/v1"   # любой OpenAI-совместимый шлюз
export LLM_API_KEY="..."
export LLM_MODEL="gpt-4o-mini"
```

При недоступности модели или неудачной проверке заземления бот автоматически
возвращается к экстрактивному ответу — демонстрация не ломается.

## 5. Структура проекта

```
assistant/
  text.py           нормализация: стеммер Портера, стоп-слова, синонимы
  kb.py             загрузка базы знаний, слияние слоёв, лексикон
  retriever.py      гибридный поиск и сигналы уверенности
  pipeline.py       политика ответа, уточнения, отказы, эскалация
  llm.py            опциональная генерация + проверка заземления
  telegram_bot.py   клиент Telegram Bot API, long polling, кнопки
  web.py            Flask: демо-чат, /api/ask, вебхук
  config.py         пороги и настройки (переопределяются переменными среды)
data/
  source/khakaton.xlsx        исходный файл задания
  kb/base_from_xlsx.json      автогенерация из Excel (дословно)
  kb/curated.json             редакторский слой: атомарные документы
  kb/clarify.json             варианты ответа и слоты уточнений
  kb/domain_lexicon.json      лексикон предметной области
tools/build_kb.py             пересборка базового слоя из Excel
eval/                         наборы оценки и скрипт метрик
tests/                        модульные тесты
web/index.html                интерфейс демо-чата
```

### Как база знаний связана с исходным Excel

`tools/build_kb.py` превращает каждую строку Excel в документ (`q01…q21`)
дословно. Редакторский слой `curated.json` разбивает объёмные ответы на
атомарные документы, добавляет перефразировки и ключевые слова; поле
`replaces` указывает, какой автогенерированный документ он замещает, поле
`source_row` — строку исходного файла. Тест
`test_all_21_source_rows_covered` следит, что ни одна строка Excel не потеряна.

Поле `grounding` отражает надёжность: `npa` — есть нормативный акт,
`official` — официальный источник без НПА, `none` — прямой нормы нет, и тогда
ответ содержит явную оговорку об этом (вопросы про «зелёный экран»,
задержку уведомления и повторное списание).

## 6. Что стоит доработать после хакатона

- Векторный поиск (эмбеддинги `sbert_large_nlu_ru` или `multilingual-e5`) как
  четвёртый сигнал — заметно поднимет Doc@1 на вопросах «на стыке» тем.
- Автоматическое обновление базы: тарифы меняются постановлениями, нужен
  парсер официальных публикаций и дата актуальности у каждого документа.
- Полноценная передача диалога оператору (тикет с историей), а не только
  выдача контактов.
- Журналирование обращений и дообучение словаря синонимов на реальных
  формулировках пассажиров.
- Интеграция с РНИС ТО для ответов о конкретном рейсе в реальном времени.
